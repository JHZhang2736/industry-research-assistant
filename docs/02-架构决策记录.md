## ADR-001：为什么放弃 LangGraph 执行器，改用手写 `_run_simplified`

### 背景

`backend/app/service/deep_research_v2/graph.py` 同时存在两条执行路径：

- `_run_with_langgraph()`：基于 LangGraph `StateGraph.astream()`
- `_run_simplified()`：基于 `asyncio.Queue` 的手写状态机

代码里 LangGraph 路径被注释掉，**始终走 `_run_simplified`**：

```python
# 始终使用手写版本执行（支持实时SSE流式输出）
# LangGraph 版本会批量处理消息，无法实现实时流式输出
async for event in self._run_simplified(state):
    yield event
```

### 原作者面临的问题

LangGraph 当时版本（`>=0.0.20`，2024 年初）的 `astream()` 只支持三种 stream_mode：

| 模式 | 颗粒度 |
|------|--------|
| `values`（默认） | **节点完成后**整状态 |
| `updates` | **节点完成后**只推 diff |
| `debug` | 调试事件 |

业务需求是「Scout 正在搜索…已找到 3 篇…正在提取…」**节点内**每一步都要推给前端。而 LangGraph 当时只能"节点级"：Scout 跑 30 秒，30 秒内前端**啥也看不到**，结束才一口气推 20 条消息。

### 当时的决策

放弃 LangGraph 的执行器，自己用 `asyncio.Queue` 做"边执行边吐":

- **Agent 内**（`base.py::add_message`）：每产出事件 `put_nowait` 进队列
- **Graph 层**（`graph.py::_run_simplified`）：在 agent 后台 task 进行时，主循环每 0.5s 从队列取消息 yield 给前端

### 代价

- 200+ 行手写状态机
- state 里塞了一个 `asyncio.Queue` 对象（`state["_message_queue"]`），导致 state **不可 JSON 序列化**，每次保存检查点要小心绕开
- 检查点、取消、路由全部自己实现（`checkpoint_service.py` + Redis cancel flag + `if state["phase"] == ...`）
- LangGraph 的 StateGraph 仍在 compile，实际是死代码

### 结论

**在原作者的版本下，决策合理**。但这个限制已被新版 LangGraph 解决——见 ADR-002。

## ADR-002：是否升级到 LangGraph 0.2+ 并重新使用其执行器

### 新的可能性

**LangGraph 0.2.x（2024 年中）引入了 `stream_mode="custom"` + `get_stream_writer()`**，让节点内任意位置可以手动推事件。本质和当前 `asyncio.Queue` 是同一个思路，但由框架托管。

```python
from langgraph.config import get_stream_writer

async def research_node(state: ResearchState) -> dict:
    writer = get_stream_writer()
    writer({"type": "phase", "phase": "researching", "content": "开始搜索..."})

    for i, query in enumerate(queries):
        results = await bocha_search(query)
        writer({"type": "search_progress", "current": i + 1, "total": len(queries)})
        # ... 节点正在跑，但每条都立刻流出

    return {"facts": all_facts}

# 调用层
async for mode, chunk in graph.astream(
    initial_state,
    stream_mode=["custom", "updates"],
    config={"configurable": {"thread_id": session_id}}
):
    if mode == "custom":
        yield format_sse(chunk)
    elif mode == "updates":
        await save_checkpoint(...)
```

迁移成本：把 `BaseAgent.add_message(state, type, content)` 替换为 `writer({...})`，写法几乎一致。

### 真 LangGraph 能消除的自研负担

| 当前自研 | LangGraph 0.2+ 替代 | 收益 |
|---------|--------------------|------|
| `_run_simplified` 200+ 行手写 | `StateGraph` + 条件边 | 代码减少 60%+，DAG 可视化 |
| `checkpoint_service.py` + `research_checkpoints` 表 | `AsyncPostgresSaver` | 官方实现，自带 thread_id 隔离、time-travel、resume |
| Redis cancel flag + 0.5s 轮询 | `asyncio.CancelledError` / `interrupt()` | 标准中断机制 |
| `_should_revise` 手写函数 | `add_conditional_edges` | 拓扑显式可见 |
| `state["phase"]` 字段手工维护 | 节点位置即 phase | 少字段、少 bug |
| `state["_message_queue"]` 污染 state | `get_stream_writer()` 走 contextvars | state 可序列化 |

### LangGraph 仍给不了的能力

**只有一点**：0.5 秒级的主动取消轮询。LangGraph 的取消依赖 `await` 点的 `asyncio.CancelledError` 传播，如果节点内某段同步代码（如 `trafilatura.extract`）卡 5 秒，那 5 秒内取消信号收不到。

> **缓解**：在节点内的循环里仍可主动 check 取消标志，并不算 LangGraph 的硬伤。

### 备选路线对比

| 路线 | 描述 | 适合场景 |
|------|------|---------|
| **A. 删除 LangGraph** | 干净使用 `asyncio.Queue`，删 `_build_langgraph` / `_run_with_langgraph` / 死代码 | 个人维护、不在意生态、追求极简 |
| **B. 升级 + 真用 LangGraph 0.2+** | `custom` 流式 + `PostgresSaver` + 条件边 | 团队协作、有学习/演进诉求、想接生态工具 |

### 推荐：路线 B

理由：

1. **可发现性**：新人看到 LangGraph 知道是标准 DAG 框架；看 `_run_simplified` 200 行 if/elif/while 要花一小时读懂
2. **官方迭代**：LangGraph 在快速演进，2026 年已支持 streaming、checkpointer、interrupt、subgraph、parallel branch、Send API（动态 fan-out，正好能做章节级并行搜索）
3. **学习价值**：项目源自「Agent 实战课」，真正用上 LangGraph 比自研更符合学习目标
4. **生态工具**：LangSmith 调试、LangGraph Studio 可视化、官方 checkpointer 实现都白嫖

### 反推：路线 A 何时合理

- 项目此后封板，不再演进
- 单人维护，无新人加入
- 想最大化代码自包含、最小化依赖

## ADR-003：迁移到 LangGraph 0.2+ 的执行计划

### 阶段一：引入 custom stream（1-2 天，零风险）

**目标**：在不删除 `_run_simplified` 的前提下，让 `_run_with_langgraph` 跑通同等流式效果。

**步骤**：

1. 升级依赖：
   ```
   langgraph>=0.2.40
   ```

2. 改造 `BaseAgent.add_message`（兼容两条路径）：
   ```python
   def add_message(self, state, event_type, content):
       message = {"type": event_type, "agent": self.name, "content": content, ...}
       state["messages"].append(message)
       try:
           from langgraph.config import get_stream_writer
           writer = get_stream_writer()
           writer(message)
       except RuntimeError:
           # 不在 graph 上下文里（如直接调用 agent 测试），降级
           if state.get("_message_queue"):
               state["_message_queue"].put_nowait(message)
   ```

3. 修改 `_run_with_langgraph` 使用 `stream_mode=["custom", "updates"]`

4. 启用 LangGraph 路径，把 `_run_simplified` 路径加 feature flag 控制

5. 测试一次完整的研究任务，前后端体验对比

6. 验证通过后，**删除 `_run_simplified` 及相关辅助代码**

**风险**：低。两路径并存期间可随时回滚。

### 阶段二：替换检查点和取消（3-5 天）

**目标**：用 LangGraph 官方机制替换 `checkpoint_service` 和 Redis cancel flag。

**步骤**：

1. 引入 `AsyncPostgresSaver`：
   ```python
   from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

   async with AsyncPostgresSaver.from_conn_string(DB_URL) as saver:
       graph = workflow.compile(checkpointer=saver)
   ```

2. `research_checkpoints` 表保留作业务侧附加信息（如 `final_report`、`ui_state_json`），核心 state 交给 LangGraph 表

3. 取消机制：用 `task.cancel()` + 节点内 `await` 点的 `CancelledError`；Redis 标志位作为「跨进程取消」的兜底保留

4. `state["phase"]` 字段移除，改为从 LangGraph 的当前节点推导

**风险**：中。涉及数据迁移和并发取消语义变更，需要充分测试 resume 流程。

### 阶段三（可选）：用 Send API 改章节并行

**目标**：把 Scout 阶段从「串行多 query」改为「多 section 并行」。

**思路**：

```python
from langgraph.types import Send

def fan_out_sections(state: ResearchState):
    return [
        Send("search_section", {"section": sec, "state": state})
        for sec in state["outline"]
    ]

workflow.add_conditional_edges("plan", fan_out_sections)
workflow.add_edge("search_section", "merge_results")
```

**收益**：研究时间从「6 个章节串行」缩短到「max(单章节时间) + 合并」。

**风险**：中。LLM 并发调用要考虑配额、限流、合并冲突。

## ADR-004：保留多 Agent 设计 vs 折叠成单一长 prompt

### 背景

当前 6 个 Agent（Architect / Scout / DataAnalyst / Wizard / Critic / Writer）每个都是独立的 LLM 调用，prompt 模板独立。也可以考虑把它们合并成 1-2 个更强的 Agent（如 Claude Opus / GPT-5 级别）走单 prompt 完成全流程。

### 维持现状的理由

1. **每 Agent 模型可调**：Scout 用 qwen-plus 省钱，Writer 用 deepseek-v3.2 + 16k tokens
2. **失败隔离**：某个 Agent 出错只影响该阶段
3. **可观测性**：每个阶段独立日志、独立 token 统计
4. **演进性**：未来要替换某个 Agent 实现（如 Critic 接外部 fact-check API）改动小

### 折叠的代价

- 失去模型混搭能力
- prompt 变得极长、易超 context
- 调试困难（只能看最终输出，看不到中间推理）

### 结论

**保留多 Agent 架构**。但可以考虑：
- 让用户选择「快速模式」（Architect → Scout → Writer，跳过 Analyze 和 Review）
- 让用户选择「精研模式」（默认全流程 + max_iterations=3）
