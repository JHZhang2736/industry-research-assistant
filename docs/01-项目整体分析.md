# 行业信息助手 — 整体分析（后端为主）

> 分析范围：`backend/` 目录的核心后端实现，前端仅做简要说明。
> 文档目的：作为后续优化、改造、新功能开发的基线参考。

---

## 一、项目定位与核心需求

这是一个面向**垂直行业（智慧交通 / 金融科技 / 医疗健康 / 能源电力）研究分析人员**的 AI 深度研究助手。核心目标：用多智能体协作的方式，自动完成「行业问题 → 资料搜集 → 数据分析 → 撰写带数据/图表的研究报告」的端到端流程。

### 核心功能模块

| 模块 | 说明 |
|------|------|
| **DeepResearch V2 深度研究** | 核心卖点。多 Agent 协作产出带数据图表、参考文献、知识图谱的研究报告；支持 SSE 流式输出、断点续作、人工取消 |
| **多轮对话 (Chat)** | RAG（政策文档索引）+ Web 搜索 + 附件问答的混合问答，流式输出 |
| **知识库管理** | 个人知识库 + 文档上传（DocMind 解析 → 向量化 → Milvus & Elasticsearch 双写） |
| **行业资讯采集** | 每日 12:00 定时调度，按行业关键词从 Bocha（资讯）+ 81API（招投标）抓取并入库 |
| **数据库探索 / Text2SQL** | 暴露 PG 表结构 + 自然语言转 SQL 查询行业统计 / 企业 / 政策数据 |
| **长期记忆 (LongTermMemory)** | 历史会话摘要 + 关键洞察落到 PG，向量存到 Milvus，跨会话召回 |
| **用户体系** | JWT 鉴权、用户/会话/附件/知识库的标准多租户结构 |

## 二、技术栈

### 后端

- **Web 框架**：FastAPI + Uvicorn（异步）
- **ORM**：SQLAlchemy 2.x + Alembic
- **认证**：python-jose (JWT) + passlib (bcrypt)
- **LLM 接入**：OpenAI SDK（DashScope OpenAI 兼容模式），主用 `deepseek-v3.2`、`qwen-plus`；可选 OpenRouter 网关
- **Agent 编排**：**LangGraph**（StateGraph + END + 条件边），同时实现了「简化手写版」以支持真正实时的 SSE 流
- **RAG / 索引**：LlamaIndex + DashScope Rerank
- **流式**：Server-Sent Events（FastAPI StreamingResponse + asyncio.Queue）
- **网页抓取**：trafilatura + BeautifulSoup + requests/httpx
- **文档解析**：阿里云 DocMind + PyPDF2 / python-docx / openpyxl
- **NLP**：jieba、tiktoken、nltk
- **数据/可视化**：pandas、numpy、matplotlib、seaborn、wordcloud（CodeWizard 沙箱内执行）
- **定时任务**：APScheduler（AsyncIOScheduler + CronTrigger）

### 基础设施（docker-compose）

- **PostgreSQL 15**：业务主库
- **Redis 7**：缓存 + **研究取消标志位**（`research:cancel:{session_id}`）
- **Milvus 2.3.3 (+ etcd + MinIO)**：向量库（embedding 维度 1024，对应 `text-embedding-v4`）
- **Elasticsearch 8.11**：全文检索 / DocMind 解析后存入的索引（`policy_documents`、`kb_<name>`）

### 外部 API

- DashScope（LLM + Embedding + Rerank）
- Bocha（资讯 / Web 搜索）
- 81API（招投标）
- 聚合数据（股票行情）
- 阿里云 DocMind（文档解析）

## 四、Agent 架构（核心）

### 工作流（LangGraph StateGraph）

```
            ┌──────────┐
START ─→──→ │  plan    │ ChiefArchitect  生成大纲 + 假设 + 关键词
            └────┬─────┘
                 ↓
            ┌──────────┐
            │ research │ DeepScout       Web / 本地并行搜索、原文阅读、信源评级、提取 facts
            └────┬─────┘
                 ↓
            ┌──────────┐
            │ analyze  │ DataAnalyst → CodeWizard   提取数据点 + 知识图谱，Python 沙箱出图
            └────┬─────┘
                 ↓
            ┌──────────┐
            │  write   │ LeadWriter      章节化撰写 Markdown 报告
            └────┬─────┘
                 ↓
            ┌──────────┐    needs_revision
            │  review  │ ──────────┐    CriticMaster  对抗式审核，给质量分
            └────┬─────┘           │
                 │ pass            ↓
                 ↓           ┌──────────┐
                END          │ revise   │ 回到 review；超 max_iterations 强制 END
                             └────┬─────┘
                                  │
        (智能路由：缺信息→走 re_research→write；只需文字→走 revise)
```

### 6 个 Agent 角色

| Agent | 类 | 模型 (温度) | 职责 |
|-------|----|-----------|------|
| **ChiefArchitect** 总架构师 | `architect.py` | deepseek-v3.2 (0.7) | 意图解码、生成研究大纲(6 章节)、产出 3 条研究假设、子问题、关键词 |
| **DeepScout** 深度侦探 | `scout.py` | qwen-plus (0.5) | 并行搜索（Bocha web + Milvus 本地知识库），trafilatura 读原文，给来源打可信度分(0-1)，提取结构化 Fact |
| **DataAnalyst** 数据分析师 | `data_analyst.py` | deepseek-v3.2 (0.3) | 从 facts 抽取 DataPoint（指标 / 值 / 单位 / 年份），构建知识图谱节点和边 |
| **CodeWizard** 数据极客 | `wizard.py` | deepseek-v3.2 (0.3) | **唯一可执行 Python** 的 Agent，沙箱内跑 matplotlib，产 base64 图表 + ECharts option |
| **LeadWriter** 首席笔杆 | `writer.py` | deepseek-v3.2 (0.7), 16k tokens | 按章节合成 Markdown 报告，规范引用 |
| **CriticMaster** 毒舌评论家 | `critic.py` | deepseek-v3.2 (0.5) | 对抗式审稿：幻觉 / 缺源 / 逻辑 / 偏见 / 时效；输出 1-10 质量分 + 是否需要补搜 |

### 关键设计亮点

1. **全局状态机 (Global Working Memory)** — `ResearchState: TypedDict`，所有 Agent 共享读写：query / outline / facts / data_points / charts / draft_sections / final_report / critic_feedback / quality_score / messages 等约 25 个字段；用枚举 `ResearchPhase` 跟踪阶段。

2. **双执行路径** — 真正运行的是 `_run_simplified`（手写流程 + `asyncio.Queue`），而非 `_run_with_langgraph`。代码注释明确说明 LangGraph 的 `astream` 会批量产消息，无法实时推 SSE。`BaseAgent.add_message` 在写 state 的同时 `put_nowait` 到队列，graph 层在 agent 任务进行中持续 `get` 出来 `yield` 给前端。

3. **可控的循环** — `_should_revise` 根据 `unresolved_issues > 0 and iteration < max_iterations` 决定回到修订；critic 还能把 phase 设为 `RE_RESEARCHING` 触发「补搜→改写」路径，比单纯「重写」更聪明。

4. **检查点持久化** — 每个阶段结束写 `research_checkpoints` 表（`state_json` + `ui_state_json` + `final_report`），支持 `/research/resume/{session_id}` 从任意阶段续跑、前端刷新后恢复研究步骤/搜索结果/图表/报告全部 UI 状态。

5. **可取消** — Redis 写 `research:cancel:{session_id}` 标志位，每个 agent 启动前 + 0.5s 队列轮询时都 `check_cancelled()`，前端调 `POST /research/cancel/{session_id}` 立即响应。

6. **基类的健壮性** — `BaseAgent.parse_json_response` 用 5 段防御解析 LLM 输出（直接解析 → markdown 代码块 → 最外层花括号 → 修复尾逗号/缺逗号/无效转义 → ast.literal_eval），是常见 Agent 项目里相对完整的 JSON 容错。

7. **每 Agent 独立模型配置** — `AgentsConfig` 让搜索阶段用更快的 qwen-plus，分析/写作用 deepseek-v3.2，writer 给到 16k tokens，节省成本同时保质。

## 五、深度研究的端到端数据流

```
前端 POST /research/stream  {query, session_id, search_modes:[web,local]}
        ↓
research_router → DeepResearchV2Service.research()
        ↓ AsyncGenerator
DeepResearchGraph._run_simplified()
   ├─ create_initial_state() / load_checkpoint()
   ├─ phase=planning   → Architect.process(state)   ── 队列 ── SSE
   ├─ checkpoint_save  (PG: research_checkpoints)
   ├─ phase=researching → Scout.process(state)
   │     ├─ Bocha API 并行多 query
   │     ├─ trafilatura 抓原文
   │     └─ (可选) Milvus 本地知识库检索
   ├─ phase=analyzing  → DataAnalyst → CodeWizard (Python 沙箱出图)
   ├─ phase=writing    → LeadWriter (Markdown 章节合成)
   ├─ loop:
   │     phase=reviewing → Critic
   │     ├─ verdict=pass → break
   │     ├─ RE_RESEARCHING → Scout 补搜 → Writer 重写
   │     └─ REVISING      → Writer 修订
   └─ 完成 → research_complete 事件（report + charts + references + score）
```

## 六、当前架构的局限与潜在优化方向（先记录，后续讨论）

1. **LangGraph 实际未用其执行能力** — 手写循环已能完成所有调度，langgraph 依赖可能可移除；或反过来真正用上其 checkpoint、interrupt、time-travel 能力替换自研实现。
2. **`_run_simplified` 体量过大** — 一个方法承担：状态机推进 / 取消检查 / 队列消费 / UI state 同步 / 检查点落库 / 引用结构转换。建议拆分。
3. **每阶段串行执行** — Scout 内部已经并行，但章节之间是否也能并行？比如多个 section 同时搜索。
4. **CodeWizard 的代码执行是同进程 `exec`** — 没有真正的沙箱（资源/网络/文件限制），风险偏高。
5. **Architect 大纲固定 6 节** — 通过 prompt 模板硬编码 sec_1～sec_6，难以适应复杂或简单课题。
6. **关键词配置硬编码** — `industry_config.py` 写死 4 个行业，扩展性差，应入库管理。
7. **JSON 输出依赖 `response_format=json_object`** — 强模型才稳定，弱模型容易报错，目前靠 `parse_json_response` 兜底但成本高。
8. **检查点字段重复** — `state_json` 和 `ui_state_json` 大量字段语义重叠（charts / references / facts 都同时存在），有数据一致性风险。
9. **资讯采集错误处理较弱** — `news_collection_service` 单次失败可能整体 fail，且没有去重/增量策略的详细审视。
10. **前端 UI 状态深耦合** — 后端要为前端构造 `ui_state.research_steps / search_results / charts / references`，违反「后端只关心数据，UI 自己拼」的原则。
11. **测试缺失** — `backend/test/` 仅有零散脚本，没有单元/集成测试。
12. **可观测性薄弱** — 日志 INFO 级别打得多，但缺统一 trace_id、Token 用量统计、各 Agent 耗时聚合视图。

## 七、术语速查

- **SSE**：Server-Sent Events，单向流式推送。前端用 EventSource 接。
- **Fact**：经过 LLM 抽取的「带来源 + 可信度评分」的结构化事实。
- **DataPoint**：可量化的数据点（指标/数值/单位/年份）。
- **Section**：报告章节，含 id / title / 是否需要图表 / 是否需要数据 等元信息。
- **ResearchPhase**：研究阶段枚举（init / planning / researching / analyzing / writing / reviewing / re_researching / revising / completed）。
